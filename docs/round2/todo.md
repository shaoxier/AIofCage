## 三、逐条 todo

### 1. 首次准备的下载失败

**现状**

首次启动要下载的东西里，最容易在国内网络失败的几处（按可能性排序）：

1. **VM 系统镜像**
   - 约 317 MiB，从 GitHub Releases 下载，地址写死在 colima 里。
   - 应用剥掉了代理变量（`tools.go:85`），新建 VM 硬超时 20 分钟（`environment.go:112`）。平均速度低于约 270 KiB/s 就会超时。
   - 期间界面一直只显示“检查专用虚拟机”。
2. **门卫镜像的 apt**
   - 还在用 `deb.debian.org`（`gatekeeper/Dockerfile:4`），而门卫是首次启动时第一个构建的镜像（`manager.go:408`）。
   - 之前换阿里云源的提交 d1e4412 只改了 agent 镜像。验收记录里，官方源 15 秒只收到约 151 KB。
3. **npm**
   - 全部走 `registry.npmjs.org`，没有 lockfile，每一步都清缓存（`agent/Dockerfile.tmpl:15-18`），失败重试要从零下载。
   - filesystem MCP 不管用不用都会装，实测耗时 218 秒。
4. **应用外的依赖**：Homebrew 及其安装包；源码构建时的 Go 模块（README 没提 goproxy.cn）。
5. **其他**
   - ECR Public 上的基础镜像偶尔不稳。
   - 整体超时 40 分钟（`sandboxes.go:104`），可能被 VM 的 20 分钟加构建的 30 分钟吃满。
   - 用户 `~/.docker/config.json` 里的凭据助手、代理和 CLI 钩子会混进构建，钩子的提示可能把真正的错误挤掉。
   - VM 磁盘只有 40 GiB，旧镜像从不清理。本机已有 26.86 GB 镜像和 14.74 GB 构建缓存。

另外，教程的界面验收用的是模拟后端（`docs/onboarding.md:42`），从没在真实下载下完整走过一遍。

**要做**

快修：
- [ ] 门卫镜像换国内源；或者去掉 apt，把根证书编进门卫二进制，改用 `FROM scratch`。
- [ ] npm 改用国内镜像（npmmirror），失败时回退官方源；去掉 `npm cache clean`，改用构建缓存挂载（要先确认有 buildx）。
- [ ] 按 agent 版本生成 lockfile，改用 `npm ci`。包的完整性由 lockfile 里的 sha512 保证，换镜像源也不降低安全性。
- [ ] filesystem MCP 只在启用时安装；装完执行 `codex --version` 这类自检，避免平台二进制没下全，镜像却显示“构建成功”。
- [ ] 子进程环境加上 `DOCKER_CLI_HOOKS=false` 和 `DOCKER_CLI_HINTS=false`。

预下载与预检：
- [ ] **第 1 步就开始准备运行环境。** 检测通过后，在后台下载 VM 镜像、拉取基础镜像和门卫镜像，带进度、能停止、失败可重试。用户在第 2、3 步配置时下载同时进行，到第 4 步多半已经下完。agent 镜像要等第 3 步选定智能体后再构建。
- [ ] **VM 系统镜像由应用自己下载。**
  - 国内地址（例如七牛对象存储）优先，GitHub 作为回退；支持断点续传。
  - 用 colima 内置的 sha512 校验后，通过 `--disk-image` 传给 colima（本机 colima 0.10.3 支持这个参数）。校验在本机完成，所以镜像源本身不需要被信任。
  - 要维护一张“colima 版本 → 镜像地址和 sha512”的对照表，查不到就走默认下载。
- [ ] **第 1 步增加预检。**
  - 检查项：macOS 13 以上（vz 和 virtiofs 的要求，代码现在只查 darwin/arm64）、buildx、宿主和 VM 的剩余空间、各下载源能否连通和大致速度。
  - 写明首次大约要下载多少、要等多久，数字按实测填，不先估。
- [ ] **依赖缺失时给出完整引导。**
  - 检测是否装了 Homebrew，命令旁加复制按钮，附国内 Homebrew 镜像的说明。
  - 用 brew 装的 docker 不带 buildx，提示一起装 `docker-buildx`。
- [ ] **错误可读。**
  - 完整输出脱敏后写进应用数据目录。
  - 按 DNS、超时、TLS、磁盘满、哈希不符、429 分类，给出中文说明和下一步。
  - 网络瞬时错误自动退避重试 1～2 次。
  - 超时改为看“多久没有进展”，而不是总时长。
- [ ] 只清理带 `io.aiofcage.managed` 标签的旧镜像和构建缓存，清理前先列出要删什么。

进阶（时间够再做，对应交接包 A03、方向文档 P0-5）：
- 预构建镜像按摘要拉取，或从离线包导入，本地构建作为回退。
- 把 colima 和 lima 打包进安装包。

**验收**：新建一个 macOS 测试账户，用 Network Link Conditioner 限速，从第 1 步走到第 5 步，中途不需要打开终端处理报错；分别记录首次启动和缓存命中两种情况的耗时。

**分支**：`fix/first-run-mirrors`（快修）、`feat/vm-image-prefetch`。

### 3. 七牛厂商快捷选项

**现状**
- **预设只有 Codex 一条。** 名为“七牛 xapi（比赛接口）”（`presets.json:2-12`），默认勾选钥匙串里的比赛 key。Claude Code 和 dsh 都没有七牛预设。
- **llmapi 需要另配 key。** `llmapi.qiniu.io` 是七牛的 XHub 网关，内核是 LiteLLM，OpenAI Chat、Responses、Anthropic Messages 和 `/v1/models` 都支持。实测比赛 key 在它上面返回 401（`token_not_found_in_db`），**需要另配一个 llmapi 能用的 key**。比赛 key 只在 `xapi.qiniu.io` 上有效。
- **llmapi 和 xapi 都不在七牛的公开文档里。**
  - 公开产品是 `api.qnaigc.com`（海外是 `api.modelink.ai`）。它的 Responses 接口不在 `/v1/responses`，要走 `/bypass/openai/v1`。
  - CC Switch 和 Cherry Studio 里的“七牛云”预设，用的都是 `api.qnaigc.com`。
- **CC Switch 的做法**：先选厂商（可搜索、分组），再填表单。预设会带入地址、协议、认证方式、默认模型和“获取 API Key”的链接，用户通常只需要填 key。
- **同题作品里已经有人做了**：七牛预设同时提供 `api.qnaigc.com` 和 `llmapi.qiniu.io`，并提示“两套 key 不互通”。我们至少要做到同样程度。

**要做**
- [ ] 预设改名为“七牛云”，三个智能体各一条，各自保存完整地址：

| 智能体 | 默认地址（按会议用 llmapi） | 协议 | 门卫放行 |
|---|---|---|---|
| Codex | `https://llmapi.qiniu.io/v1` | Responses | `POST /v1/responses/*`、`GET /v1/models` |
| Claude Code | `https://llmapi.qiniu.io` | Anthropic | `POST /v1/messages/*`、`GET /v1/models` |
| dsh | `https://llmapi.qiniu.io/v1` | OpenAI Chat | `POST /v1/chat/completions`、`GET /v1/models` |

- [ ] 提供三个地址候选：
  - llmapi：默认。
  - `api.qnaigc.com`：公开地址，Codex 要用 `/bypass/openai/v1`。
  - `xapi.qiniu.io`：只给比赛 key 用。
- [ ] 新预设不再默认勾选比赛 key。只有选了 xapi 时才允许用钥匙串里的比赛 key，而且只能发往 xapi。
- [ ] 兼容旧预设 ID `qiniu-xapi`，否则已保存的供应商在编辑时会找不到预设（`providers.js:116`）。新增 `qiniu-claude`、`qiniu-dsh`。
- [ ] 预设卡片改成厂商快捷选项：
  - 显示厂商名和图标、获取 key 的链接、“只需填写 API Key”的提示。
  - 默认模型不写死，填完 key 后自动拉取模型列表（见第 5 条）。

### 4. 终端右侧文件栏

**主流软件怎么做**
- **传统 Shell 软件**：MobaXterm、FinalShell、WindTerm、Xshell + Xftp、Tabby 的文件面板，其实是远程 SFTP 浏览器。“跟随终端当前目录”要靠 shell 主动上报，厂商自己也标为实验性功能。iTerm2 的侧边工具栏里没有文件树；3.7 版给 Claude Code 会话配了一个并排的 Diff 会话。
- **Agent 工作台**：Codex app、Cursor 3、Conductor、Zed、Warp 的共同做法是：
  - 右侧面板先放“变更”，再放项目文件树；
  - 根目录固定为项目，不跟随当前目录；
  - 路径可以插入或拖进输入框；
  - 面板能收起，多数能拖宽。

**现状**：后端没有任何列目录或读文件的接口，只有“在访达中打开项目”和定位审计日志两个功能。项目在宿主和容器里是同一个绝对路径（`manager.go:543`），宿主可以直接读，沙箱停止时也能浏览。

**第一版建议**

```text
┌ 终端 ──────────────────────────────────┬ 项目文件 ─────── [刷新][收起] ┐
│ [Codex 1 ✕][Codex 2 ✕][+ 新建 ▾]        │ [变更 3] [全部文件]            │
│                                         │  M  src/main.go     +12 −3    │
│   结构化对话视图（现有）                 │  A  docs/plan.md    +40       │
│                                         │  ── 只读预览 / 只读 diff ──    │
│ ┌ 输入框（可从右侧拖入文件路径）──────┐ │                               │
└─────────────────────────────────────────┴───────────────────────────────┘
```

- [ ] **面板本身**：放在右侧，可收起、可拖宽（240～480 px）；窗口较窄时默认收起；按沙箱记住展开状态和宽度。
- [ ] **“变更”标签**：显示 Git 状态字母和增删行数，点开看只读 diff；项目不是 Git 仓库时隐藏这个标签。
- [ ] **“全部文件”标签**：按需逐层加载，目录排在前面；`node_modules`、`.git` 等默认折叠；每层设条目上限；可以切换是否显示隐藏文件。
- [ ] **操作**：插入路径（点按钮或拖进输入框，只插入项目内相对路径的文本）、复制路径、在访达中显示。第一版不做编辑、新建、重命名和删除。

  - `ListProjectEntries`：列出目录内容。
  - `ReadProjectFile`：只读常规文件，上限 512 KiB，区分文本、图片和二进制。
  - `RevealProjectPath`：只做 `open -R`，即在访达中显示。
- [ ] **刷新方式**：
  - 每轮对话开始和结束时，各做一次有上限的文件元数据快照并求差。文案写“本轮期间项目内的改动”，因为多个会话并行时分不清是谁改的。
  - 要不要加文件监听，先实测 virtiofs 下容器里的写入能否触发宿主的文件事件。
- [ ] **布局**：
  - 在标签栏下面加左右两列。

**必须一起交付的安全约束**
- **不在宿主上对项目目录运行 git。**
  - 原因：agent 能改写 `.git/config`，借助 `core.fsmonitor`，宿主上的一次 `git status` 就能执行任意命令。今年已经出现多个同类漏洞。

**验收**

- 拖入的路径，三种 agent 都能正确读取。

### 7. 创建沙箱时的开发环境 + P0-2

**结论**：每个镜像里本来就有 node 和 npm，卡住的是网络和门卫本身。要拆成三件事来做：
1. **网络预设**：不用重建镜像，沙箱运行中就能热更新。
2. **工具链档位**：需要重建镜像。
3. **GitHub 凭据**：私有仓库需要钥匙串加 Basic 认证注入，属于 P0-3，可以后做。公开仓库的只读克隆放进网络预设。

**现状**
- **镜像和运行环境**
  - 镜像里有 Node 24、npm、git、curl、python3（没有 pip 和 venv）、ripgrep；没有编译工具链、gh、Go、Rust、Java（`Dockerfile.tmpl:6-9`）。
  - 运行时用不了 apt，原因有三：agent 不是 root；根文件系统只读；apt 源是 http，而门卫拒绝明文 HTTP。
- **创建对话框和规则来源**
  - 创建对话框只能选项目、智能体、供应商、MCP 和额度（`sandboxes.js:198-315`）。
  - 门卫规则只来自供应商和 MCP（`manager.go:650,676`），所以 `npm install` 第一步就会被 403 拒绝。
- **门卫自身会挡住常见的包请求，光加预设不够：**
  - **路径里的特殊字符**：路径中出现 `%xx`，或 `! ( ) * '` 这几个字符，就会被判为 `target_mismatch`（`proxy.go:236`）。npm 请求带 scope 的包（如 `@types/node`）时用的是 `/@types%2fnode`，Go 把模块路径里的大写字母写成 `!小写`（如 `!burnt!sushi`），两者都会中招。
  - **跳转**：所有 3xx 跳转一律改成 403（`proxy.go:448-454`），而 npmmirror 的包、GitHub release 和源码包下载都会 302 跳转。
- **路径语法写不出 GitHub 克隆规则。** 规则只支持精确路径和 `/*` 前缀，写不出克隆用的 `/*/*/info/refs`、`/*/*/git-upload-pack`，也无法单独排除推送用的 `git-receive-pack`。
- **公共主机会转发 agent 自带的凭据。** 没有绑定密钥的公共主机，会原样转发 agent 自己带的 Authorization（`proxy.go:333-344`）。
- **旧门卫不认新字段。** 运行中可以热更新规则，但应用升级后，仍在运行的旧门卫会拒收新字段（`handlers.go:105`）。
- **部分拒绝只能按域名放行。** 在建立连接阶段被拒的请求，只记录了域名，没有方法和路径。
- **403 正文太简略。**
  - 正文只有一句 `AIofCage gatekeeper: request blocked (default_deny)`。
  - npm 会显示正文里的 error，pip 只显示状态行，git 和 curl 只显示状态码。

**要做**
- [ ] 先修门卫的两处问题：
  - **路径字符**：允许字面的 `! ( ) * '`；只在 npm 的元数据路径上接受 `%2f`，解码后再匹配策略；其他编码继续拒绝。
  - **跳转**：同时满足三个条件才透传：请求没有注入凭据、目标是 https 443、目标域名也在放行名单里。不满足时返回可读的 403，并记下跳转目标的域名。
- [ ] 扩展路径语法，支持段通配 `*` 和后缀匹配，用于 GitHub 的 smart HTTP 协议。
- [ ] 新增开发源预设目录（`internal/policy/devsources.json`）。只放行 GET/HEAD，发布类接口显式拒绝：

| 生态 | 域名 | 说明 |
|---|---|---|
| npm | `registry.npmjs.org`；镜像 `registry.npmmirror.com`、`cdn.npmmirror.com` | 拒绝 PUT、DELETE 等写方法（`npm publish` 用的是 PUT）；`npm audit` 用 POST，默认不放行，做成子开关 |
| PyPI | `pypi.org`、`files.pythonhosted.org`；清华、阿里镜像 | 不放行 `upload.pypi.org`；阿里镜像必须带路径前缀 |

| crates | `index.crates.io`、`static.crates.io` | 不放行 `crates.io`，发布接口在这个域名上 |
| Maven | Maven Central、`maven.aliyun.com` | 部署用 PUT，拒绝 |

  apt 不做运行时预设，改为构建期的工具链组件。

### 8. P0-4 隔离自检

**现状**（`attacks.go` 现有 7 项检查）
- **DNS 检查永远判不了“通过”。**
  - 它要求 nameserver 全是 127.0.0.1 或 ::1（`attacks.go:233`），而 Docker 自定义网络里写的是内嵌 DNS 的地址 127.0.0.11。所以 10-25 的验收结果是“无法验证”。
  - 而且这项检查只证明了 agent 拿不到 DNS 回答，没有证明查询没有离开 VM。
- **缺少几类探针**：没有 IPv6、管理面、跨沙箱和宿主回环。早期实验包里有这些探针，但用的是实验门卫和实验拓扑，不能当作产品的证据。
- **Docker socket 只看一个路径。** 只检查 `/var/run/docker.sock`，也没有阳性样本来证明检测本身有效。
- **宿主文件检查没有区分度。** 哨兵文件放在 macOS 的临时目录，而 VM 本来就看不到那里。真正该测的是 `~/CageWorkspace` 下的其他项目。
- **结果比对和展示有缺口。**
  - 管理 token 和连接器 token 不在“输出里含真实凭据”的比对列表里。
  - 结果只保存在内存里。
  - 运行状态页的“x/y 项通过”把跳过和无法验证也算进了分母（`health.js:51`）。

**要做**
- [ ] **DNS**
  - 在出网网络上临时起一个金丝雀容器，记录收到的 DNS 查询。
  - 设两个正向对照：对照容器直接发出的查询、经内嵌 DNS 转发的查询，都必须被记到。
  - 设一个反例：在 internal 网络上起一个把 DNS 指向金丝雀的探针，它的查询必须记不到。
  - 对照不成立就判“无法验证”。
  - 验收记录里，另外用团队自有子域名的权威 DNS 做一次外部可观测的对照。
- [ ] **IPv6**
  - 检查网卡地址和路由表，主动连接公网 IPv6 地址。
  - 临时建一个开启 IPv6 的网络，做本机正向对照。
  - 公网 IPv6 要换一个有 IPv6 出网的环境来测，比如单独的 Colima profile 或一台 Linux 主机。演示机上如实写“公网 IPv6：无法验证（环境没有 IPv6 出网）”。
- [ ] **管理面**
  - agent 侧：连门卫的 8899 端口、管理地址和内部网关上的常见端口；再经代理连管理地址。预期都连不上。
  - 宿主侧对照：带 token 访问返回 200，不带返回 401；出网侧的对照容器能连上管理端口；Mac 上只在回环地址监听；用局域网 IP 连接会失败。
- [ ] **Docker socket**
  - 读挂载表，扫描所有 socket 文件和已知路径，对找到的 socket 和 2375/2376 端口发 `/_ping`，检查 `DOCKER_HOST`。
  - 准备两个阳性样本：`/tmp` 里的假 socket，以及挂了假 socket 的对照容器。两个都能检出时，阴性结论才算“通过”。
- [ ] **项目边界**
  - 把“宿主文件”拆成“Docker socket”和“项目边界”两项。
  - 项目边界的哨兵放在 `~/CageWorkspace/.aiofcage-probe-<随机串>/`：VM 里看得到，作为对照；容器里看不到，作为结论。
- [ ] **其他补充**：补上宿主回环和跨沙箱探针；把管理 token 和连接器 token 加进比对列表。
- [ ] **结果输出与展示**
  - 每项输出状态、证据、对照结果和覆盖范围。
  - 结果保存下来，可以导出 JSON。
  - 界面改成按状态计数，例如“通过 6 · 发现问题 0 · 无法验证 1 · 跳过 1”。
- [ ] **验收记录**：在 `docs/validation/` 写一份隔离闭环记录，覆盖演示机和 IPv6 环境两套，并更新验收索引。

**验收**：四类探针在演示机上给出“通过”或明确的“发现问题”；对照不成立时保持“无法验证”，不为了变绿强行判定；脚本和脱敏后的结果可以复现。

### 11. 恢复会话与多个对话

**“恢复会话”乱出现（bug，已确认）**
- **面板不判断是否真能恢复。** “可恢复会话”面板只看列表长度，不按能否恢复过滤（`sandbox-detail.js:120-121`）。
- **前端列表刷新不及时。**
  - 可恢复列表只在三个时机刷新：切换页面、沙箱操作结束、收到进度事件（`main.js:48-60`）。
  - 关掉一个发过消息的对话标签后，后端已经删了记录，前端还留着，面板马上冒出“恢复”按钮。
  - 这时点下去，如果沙箱是停着的，会先把它启动起来，然后才报“找不到可恢复的会话”。
- **后端不检查原生会话文件是否还在。** 记录还在、文件已经没了时，要等到发第一条消息才失败。

要做：
- [ ] 面板只显示真正能恢复的记录；一条都没有时，面板不出现。失效的记录放进诊断信息，不用“恢复”字样。
- [ ] 关闭标签时、首轮拿到会话 ID 后，都刷新一次可恢复列表。
- [ ] 点“恢复”时，先确认记录还在，再决定要不要启动沙箱；后端在恢复前检查原生会话文件，不存在就删掉记录并提示用户。
- [ ] 清理已删除沙箱留下的记录。会话 ID 没变时不重复写盘：现在每个 session 事件都会把 settings.json 整个重写一次（`conversations.go:273-283`）。
- [ ] 把面板的筛选逻辑抽成纯函数，补前端测试；后端补“原生会话缺失时删除记录”的单元测试。

**“Codex 对话只能创建一个”（体验问题，需要你确认当时的现象）**
- **代码本身并不限制。** 同一个沙箱可以同时开多个 Codex 对话，全应用上限 12 个（`conversations.go:121`），每个对话各自运行。
- **但看起来就像只能开一个：**
  - 每个标签都叫“Codex”（`terminal.js:120`），没有序号或时间；
  - 新建入口只在“+ 新建”下拉里；
  - 沙箱列表的“继续工作”和教程都会复用已有的标签。

要做：
- [ ] 让标签可以区分：命名为“Codex 1 / Codex 2”，或者带上创建时间；运行中的标签显示状态点。在“+ 新建”旁边加一个显眼的“新建 Codex 对话”按钮。
- [ ] 限制每个沙箱同时运行的对话数，建议 2～3 个。容器只有 2 个 CPU、4 GiB 内存、512 个进程（`manager.go:546`）。
- [ ] 实测多个 Codex 或 Claude Code 同时写 home 目录是否安全；不安全的话，给每个对话独立的 `CODEX_HOME` 或 `CLAUDE_CONFIG_DIR`。
- [ ] 在界面上提示用户：
  - 并行的对话共用项目目录和额度，同时改一个文件会互相覆盖；
  - 门卫日志目前分不出请求来自哪个对话，要分清得先做交接包的 C01。

**验收**
- 关掉标签后，不会冒出“恢复”。
- 没有可恢复的记录时，面板不出现。
- 同一个沙箱开两个 Codex 对话，各自完成一轮，标签能分清。

**分支**：`fix/conversation-recovery`、`feat/multi-conversation-tabs`。

  - 开了预设后，`npm install @types/node` 和 `go mod download github.com/BurntSushi/toml` 是否会被拦。
  - npmmirror 和 GitHub release 的下载是否返回 `redirect_denied`。
  - npm、pip、git、curl 遇到 403 时，实际打印什么。
- **全局说明**：Codex 0.164.0、Claude Code 2.1.309、dsh 0.2.1-rc.2 是否会加载各自的全局指令文件。
- **隔离**
  - 容器内 resolv.conf 的实际内容。
  - agent 的网卡有没有 IPv6 地址。
  - 内部网关上，VM 的哪些端口可达。
  - Colima 用的是哪种网络模式，VM 能否访问宿主的回环地址。
- **七牛**
  - 用 llmapi 的 key 拉取模型列表。
  - 三个智能体的流式输出、工具调用和图片输入是否正常。
  - Codex 遇到不支持的压缩接口时怎么表现。
- **多对话**：多个 Codex 或 Claude Code 同时写 home 目录时是否出错。
- **文件栏**：virtiofs 下，容器里写文件能否触发宿主的文件事件。
- **安装包**（第八节）
  - 全新账户首次打开 ad-hoc 签名的应用，系统会怎么提示，要走哪几步。
  - 包内的 limactl 重新签名后，还能不能启动 vz 虚拟机。
  - 带隔离属性（从网上下载的标记）的内嵌程序，能否被应用正常调用。
- **远程 MCP**（第八节）
  - GitHub、Notion、Linear、Sentry 的工具有没有只读标注。
  - 三款 agent 经 8890 连远程服务是否正常，包括流式返回。

### 保留意见 1：远程 HTTP MCP 与数据库连接器的权限粒度不同

现状属实，我们自己的文档里也写了（`docs/architecture-current.md:78`）：
- **数据库连接器**走门卫的 MCP 入口 8890，`tools/call` 按工具白名单放行（`internal/gatekeeper/mcp.go:125`）。连接器还有三层兜底：只读账号、有效权限检查、SQL 语法树策略。
- **远程 HTTP / OAuth MCP** 走普通代理：
  - 规则只按域名放行该路径下的 GET、POST、DELETE（`internal/mcp/mcp.go:138-139`）。门卫不解析 JSON-RPC，远程服务暴露的工具都能调，包括写工具。
  - 给远程服务设工具清单会直接报错“不支持本地工具权限列表”（`internal/mcp/connector.go:99-101`）。
  - GitHub 预设只能提示“建议只授予只读权限”，靠令牌本身的权限兜底。
- 这和我们自己的验收基线不一致。基线要求带凭据的 MCP 统一走协议网关，并且不同时开放 agent 直连的 HTTP 注入路径（`docs/requirements-and-acceptance.md:65`、`:90`）。

要做（取代第七节第 6 条，范围更大）：
- [ ] **改走 8890**：远程 HTTP / OAuth MCP 在 agent 配置里的地址改成 `http://gatekeeper:8890/mcp/<id>`，由门卫转发到远程地址并注入令牌。同时删掉该服务在代理上的放行规则，不留绕过网关的直连路径。
- [ ] **工具清单**：宿主在“测试连接”时用真令牌调一次 `tools/list`，记下工具名和服务自带的标注（`readOnlyHint`、`destructiveHint`）。
  - 默认只勾选标注为只读的工具，其余由用户逐个勾选。
  - 以后清单里出现新工具，默认拒绝，并提示用户。
  - 标注是服务方给的提示，只用来定默认值，不作为安全依据。
- [ ] **界面**：和数据库连接器共用一套工具复选框；沙箱详情里每个 MCP 都显示“已开放 x / y 个工具”。
- [ ] **审计**：远程 MCP 也记录工具名，参数和结果照旧不记。
- [ ] **OAuth**：续期后的新令牌下发到网关的连接配置，不再作为代理密钥。
- [ ] **自检**：隔离自检加一项，agent 直连远程 MCP 地址必须被拒绝。

验收：
- GitHub 远程 MCP 只开放只读工具时，`create_issue` 一类写工具被门卫拒绝，agent 收到可读的 JSON-RPC 错误，日志里有工具名。
- agent 带占位符直连 `api.githubcopilot.com` 被拒绝。
- Notion 的 OAuth 续期之后，工具仍能正常调用。

规模：3～4 天。分支：`feat/remote-mcp-gateway`。

分四档，前两档不需要 Apple 开发者账号：
1. **DMG 与 Release**（1～1.5 天）
   - `make dmg` 生成 ad-hoc 签名的 DMG 和 SHA256，GitHub Release 附下载。
   - README 顶部放下载入口，“从源码安装”挪到开发文档。
   - 首次打开会被 macOS 拦下，要配图说明“系统设置 → 隐私与安全性 → 仍要打开”。

### 保留意见 3：广泛第三方兼容

这句有两种读法，两种都是真实的缺口。

**读法一：除了演示过的几个，别的 agent 和 MCP 服务能不能用。**
- agent 固定三款：Codex 0.164.0、Claude Code 2.1.309、dsh 0.2.1-rc.2（`internal/runtime/images.go:43-45`），没有接其他 agent 的入口。议题点名的三款已经覆盖。
- 远程 MCP 只支持 `Authorization: Bearer`（`internal/runtime/manager.go:674-675`），把 key 放在自定义请求头或 URL 参数里的服务配不了。OAuth 只支持能自动注册客户端的服务。
- 带秘密的 stdio MCP 只有 PostgreSQL 一个。连接器目录写死在代码里（`internal/mcp/connector.go:44-50`），每接一个新服务都要改代码、重建镜像。
- 七牛自己的官方 MCP Server（`qiniu/qiniu-mcp-server`，MIT）就属于这一类：用 `uvx` 启动，AK/SK 通过环境变量传入。这类服务拿 AK/SK 在本地计算签名，占位符替换不起作用，只能由沙箱外的连接器代持。

**读法二：常见的第三方工具在沙箱里能不能用。** 默认拒绝下，`npm install` 第一步就会 403，第 7 条解决这一点。

要做：
- [ ] **兼容矩阵**（必做，1～1.5 天）
  - 列出主流 agent 和 MCP 服务，逐项实测，结果写成 `docs/validation/` 里的一份记录。
  - 分三类：已验证、可配置未验证、不支持（写明原因）。README 和答辩都引用它。
  - 这样“兼容性”就从一句话变成可查的证据。
- [ ] **通用连接器**（建议做，2.5～3 天；10-30 决定先不做）
  - 连接器目录改成声明式条目，写明包名、固定版本和校验值、启动命令、需要哪些环境变量（值从钥匙串取）、出网域名、默认开放的只读工具。
  - 第一个条目接七牛官方 MCP，演示“AK/SK 不进沙箱，agent 照样能用七牛存储”。
  - 连接器的出网同样要限制在该服务的域名内。
- [ ] **远程 MCP 的其他认证方式**（0.5 天；10-30 决定先不做）：网关转发时注入自定义请求头或 URL 参数，agent 那边仍然只有占位符。
- [ ] 其他 agent（如 Gemini CLI、opencode）先写进矩阵的“不支持”一栏，本轮不做。

分支：`test/compat-matrix`。另外两项先不做。
