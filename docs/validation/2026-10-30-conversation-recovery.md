# 会话恢复与标签序号验证

[验收记录索引](README.md)

## 改动

对应第二轮会议第 11 条和 [todo 清单](../round2/todo.md)第 11 项的最小版本：修好“恢复会话乱出现”，并给标签加序号。

1. **面板只显示真能恢复的会话**
   - “可恢复会话”面板只列出能恢复、而且还没打开的会话，一条都没有时面板不出现。
   - 不能恢复的旧记录（例如供应商配置已变化）收在一行“N 条旧会话记录不能继续”里，可以展开看原因，不出现“恢复”字样。
   - 筛选逻辑抽成纯函数 `recoveryPanel`。
2. **列表及时刷新**：以下几种情况，后端都会发一个事件，界面只重读可恢复列表：
   - 首轮拿到原生会话 ID，以及每轮结束；
   - 关闭标签；
   - 记录失效被删；
   - 清理已删除沙箱或供应商的记录。

   原来只在切换页面、沙箱操作结束和收到进度事件时刷新，关掉一个发过消息的标签后，面板会冒出“恢复”。
   - 关掉还在进行的对话时，后端一开始就删记录，不等停任务、清附件；界面也先把它从面板里藏起来，直到记录删掉。
   - 单独重读和整页刷新共用一个计数，晚到的旧结果不会盖掉新结果。
3. **恢复前先检查**
   - 点“恢复”时，先确认这条记录还在、还能恢复，再决定要不要启动沙箱。原来会先启动沙箱，再报“找不到可恢复的会话”。
   - 点下去就锁住按钮，连点只恢复一次。
   - 后端恢复前，在沙箱里查智能体自己的会话文件：
     - Codex：`~/.codex/sessions/<日期>/rollout-…-<ID>.jsonl`
     - Claude Code：`~/.claude/projects/<项目>/<ID>.jsonl`
     - DeepSeek Harness：`~/.dsh/sessions/<项目>/session-<ID>/`

     找不到就删掉记录，并提示“沙箱里已经没有这个会话的记录”。会话 ID 只作为 `find` 的一个参数传入，不经过 shell，而且必须是普通字符。
   - `find` 的错误输出只保留最后 64 KiB：智能体可以在会话目录里放大量读不了的文件夹，让 `find` 输出很多报错，不能因此占满桌面应用的内存。这对所有经 `runner.run` 执行的命令都适用，原来只用到错误输出的最后一行。
4. **少写盘，但不丢记录**：
   - Claude Code 的每条事件都带会话 ID，原来每条都会把整个设置文件重写一遍。现在只在 ID 变化、或者上次没写成功时写，另外每轮结束写一次，让面板按最近活动排序。
   - 读取列表时清掉已删除沙箱的记录，以及原供应商已删除的记录（绑定中的供应商删不掉，这些记录不可能再恢复）。
   - 只有确实读到沙箱或供应商已删除才清理；配置文件一时读不了或解析失败时，列表报错，记录都保留。
5. **标签序号**：同一个沙箱里，同名的标签按最小的空闲序号命名，例如“Codex 1”“Codex 2”“Shell 1”。恢复一个已结束的标签时，沿用它原来的标题和没发出的草稿。

## 自动测试

- `internal/service`：
  - 同一个会话 ID 重复出现只写一次，ID 变化才再写，关闭的会话不写；
  - 第一次写失败后，同一个 ID 下一次出现会再写；每轮结束会更新记录时间；
  - 已删除沙箱、已删除供应商的记录在读取列表时被删除；
  - 沙箱配置读不了（权限）或解析失败时，列表报错，记录保留；
  - 关闭还在进行的对话时，记录在任务停下之前就删掉；
  - 原生会话不在时，恢复会删掉记录并给出说明，而且检查的是记录里的沙箱、智能体和会话 ID；
  - 原有的恢复记录读写测试照常通过。
  - 新加的三项（配置读不了、写失败重试、关闭即删）都确认过：去掉对应修复后测试失败。
- `internal/runtime`：
  - 能找到会话、找不到、目录不存在都按“没有”处理；
  - `find` 输出两万行报错时，按“检查失败”处理，报的是最后一行；错误输出只保留尾部；
  - 不是普通字符的 ID 不查；
  - 沙箱停了报错；
  - 实际执行的命令是 `docker exec --user 1000:1000 … find <目录> -maxdepth 6 -name *<ID>* -print -quit`。
- 前端：标签编号取最小的空闲序号；恢复面板的分类。
- `make check`、`make test`（含竞态检查）、前端 `node --test` 都通过。

  - 打开中的对话已经有恢复记录时，面板不列出它；关掉标签后，模拟后端还没删记录，面板也不冒出它。

## 独立复查

请子代理在独立工作树里只读复查了一轮，后端问题用单元测试复现，前端问题在纯函数层面模拟复现。没有发现注入或其他安全漏洞；报了 2 个中、4 个低：

| 级别 | 问题 | 处理 |
|---|---|---|
| 中 | 关掉发过消息的标签后，后端要停任务、清附件后才删记录，这期间面板冒出“恢复” | 后端关闭时先删记录（末尾再删一次）；界面把刚关掉的对话藏起来 |
| 中 | 读取列表时把任何读沙箱配置的错误都当成“沙箱已删除”，永久删掉记录；打开中的对话之后不会再写回 | 一次读出全部沙箱，读不了就报错，只按确实不存在清理 |
| 低 | 第一次写记录失败后，同一个 ID 不再重试；记录时间变成首次拿到 ID 的时间 | 另记“已写入的 ID”，失败会重试；每轮结束更新时间 |
| 低 | `find` 的错误输出全部读进宿主内存，智能体能用大量报错撑大它 | 错误输出只保留尾部 64 KiB |
| 低 | 恢复一个已结束的标签时，序号会变 | 沿用原标签的标题 |
| 低（未复现） | 点“恢复”后第一次调用返回前，重复点击会再恢复一次 | 同步加锁 |

复查的其他观察也一并处理了：单独重读可恢复列表时不受整页刷新的计数保护（已改为共用计数）；原供应商已删除的记录一直留在“不能继续”里（已自动清理）。修复后没有再请子代理复查，逐条用上面的自动测试和模拟界面验证。

## 范围与限制

- **多对话的其他事项没做**：
  - 每个沙箱的对话数上限；
  - 每个对话独立的 `CODEX_HOME`；
  - 门卫日志按对话区分；
  - 显眼的“新建 Codex 对话”按钮。
- **停着的沙箱**：要启动后才能检查原生会话文件。
- **检查不了时照常恢复**：检查本身失败时（例如 docker 一时出错，或 `find` 只输出了报错），会照常恢复，由智能体在第一条消息时报错，和原来一样。智能体能让检查报“没有”，但它本来就能直接删掉自己的会话文件，不算新增的能力。
- **关掉已结束的标签不删记录**：沙箱停止后，对话标签显示“已结束”，这时关掉标签不会删记录，沙箱再启动后仍可恢复。这和“停止沙箱保留记录”的设计一致；主动关掉进行中的对话才删记录。
