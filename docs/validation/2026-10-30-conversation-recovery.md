# 会话恢复与标签序号验证

[验收记录索引](README.md)

## 改动

对应第二轮会议第 11 条和 [todo 清单](../round2/todo.md)第 11 项的最小版本：修好“恢复会话乱出现”，并给标签加序号。

1. **面板只显示真能恢复的会话**
   - “可恢复会话”面板只列出能恢复、而且还没打开的会话，一条都没有时面板不出现。
   - 不能恢复的旧记录（例如供应商配置已变化）收在一行“N 条旧会话记录不能继续”里，可以展开看原因，不出现“恢复”字样。
   - 筛选逻辑抽成纯函数 `recoveryPanel`。
2. **列表及时刷新**：以下几种情况，后端都会发一个事件，界面只重读可恢复列表：
   - 首轮拿到原生会话 ID；
   - 关闭标签；
   - 记录失效被删；
   - 清理已删除沙箱的记录。

   原来只在切换页面、沙箱操作结束和收到进度事件时刷新，关掉一个发过消息的标签后，面板会冒出“恢复”。
3. **恢复前先检查**
   - 点“恢复”时，先确认这条记录还在、还能恢复，再决定要不要启动沙箱。原来会先启动沙箱，再报“找不到可恢复的会话”。
   - 后端恢复前，在沙箱里查智能体自己的会话文件：
     - Codex：`~/.codex/sessions/<日期>/rollout-…-<ID>.jsonl`
     - Claude Code：`~/.claude/projects/<项目>/<ID>.jsonl`
     - DeepSeek Harness：`~/.dsh/sessions/<项目>/session-<ID>/`

     找不到就删掉记录，并提示“沙箱里已经没有这个会话的记录”。会话 ID 只作为 `find` 的一个参数传入，不经过 shell，而且必须是普通字符。
4. **少写盘**：
   - Claude Code 的每条事件都带会话 ID，原来每条都会把整个设置文件重写一遍；现在只有 ID 变化时才写。
   - 已删除沙箱留下的恢复记录，在读取列表时清掉。
5. **标签序号**：同一个沙箱里，同名的标签按最小的空闲序号命名，例如“Codex 1”“Codex 2”“Shell 1”。

## 自动测试

- `internal/service`：
  - 同一个会话 ID 重复出现只写一次，ID 变化才再写，关闭的会话不写；
  - 已删除沙箱的记录在读取列表时被删除；
  - 原生会话不在时，恢复会删掉记录并给出说明，而且检查的是记录里的沙箱、智能体和会话 ID；
  - 原有的恢复记录读写测试照常通过。
- `internal/runtime`：
  - 能找到会话、找不到、目录不存在都按“没有”处理；
  - 不是普通字符的 ID 不查；
  - 沙箱停了报错；
  - 实际执行的命令是 `docker exec --user 1000:1000 … find <目录> -maxdepth 6 -name *<ID>* -print -quit`。
- 前端：标签编号取最小的空闲序号；恢复面板的分类。
- `make check`、`make test`（含竞态检查）、前端 `node --test` 都通过。

## 真机验证（2026-10-30）

- **会话文件位置**：启动测试沙箱 `t2-remote-mcp`（装了三款智能体，有之前真机测试留下的会话），看了三款智能体的会话文件实际放在哪里。用真实的会话 ID 调 `NativeSessionExists`，三款都能找到；不存在的 ID 返回“没有”。
  - DeepSeek Harness 还在 `~/.dsh/storages/` 下留了一份以会话 ID 命名的缓存，所以只在 `sessions` 目录里查，避免会话删了还误判为存在。
- **界面**（模拟后端，运行中的沙箱）：
  - 终端页的恢复面板只有一条能恢复的 Codex 会话；
  - 不能恢复的那条只显示为“1 条旧会话记录不能继续”；
  - 连开两个 Codex 对话，标签依次是“Codex 1”“Codex 2”。

## 范围与限制

- **多对话的其他事项没做**：
  - 每个沙箱的对话数上限；
  - 每个对话独立的 `CODEX_HOME`；
  - 门卫日志按对话区分；
  - 显眼的“新建 Codex 对话”按钮。
- **停着的沙箱**：要启动后才能检查原生会话文件。
- **检查不了时照常恢复**：检查本身失败时（例如 docker 一时出错），会照常恢复，由智能体在第一条消息时报错，和原来一样。
