# 内部网络去掉虚拟机地址验证

[验收记录索引](README.md)

## 改动

处理[隔离检查补对照](2026-10-31-isolation-checks.md)里的顺带发现：Agent 能连到虚拟机的 SSH 端口。

1. **新建的内部网络上没有虚拟机的地址**
   - 内部网络 `aiofcage-<ID>-in` 创建时加 `com.docker.network.bridge.inhibit_ipv4=true`。Docker 29 下这样建的网络没有网关，虚拟机的网桥上没有 IPv4 地址。
   - 门卫仍固定用子网的 `.2`，带别名 `gatekeeper`，代理 8888 和 MCP 8890 都监听在这个地址上。
   - 子网的 `.1` 不再是网关，由第一个不指定地址的容器拿到，也就是 Agent。
   - 出网网络不变：虚拟机仍是那里的网关，门卫经它出网。
2. **已有沙箱下次启动时自动迁移**
   - 启动时读内部网络的设置：不是 internal 网络，或者没有这个选项，就先清掉遗留的探针，删除 Agent 和门卫容器，再删旧网络，按新方式重建。连接器也跟着重建。
   - 项目目录和 Agent 主目录卷保留；门卫还在运行时，删除前先保存用量。
   - 进度里多一行：“内部网络改为不含虚拟机的地址，重建网络、门卫和 Agent 容器（项目和主目录保留）”。
   - `specVersion` 不变：容器的创建参数没有变，重建由网络检查触发，已经是新网络的沙箱不会被多重建一次。
   - 沙箱运行中被再次启动时（例如本机 AI 控制在每次任务前调用启动）也会迁移，终端会话随 Agent 容器结束。门卫镜像更新时替换容器也是这样。
3. **隔离检查新增“虚拟机网关端口”**（第 10 项）
   - 宿主从 Docker 读两个网络的网关，也就是虚拟机在这两个网络上的地址。
   - Agent 连这些地址上的 13 个常见端口：22、53、80、443、2375、2376、5432、6443、8080、8888、8890、8899、10250。只建 TCP 连接，不发送数据。
   - **对照**：出网网络上的对照容器用同一段脚本连虚拟机在出网网络上的地址，至少要连上一个端口，证明虚拟机上确实有服务在听、探针看得见。
   - **判定**：
     - 发现问题：内部网络有网关（虚拟机在那里有地址）；虚拟机回应了 Agent 的任何一个连接（连上或拒绝连接）；Agent 网卡上有 IPv6 地址，有的话网桥的链路本地地址也可能通到虚拟机。
     - 通过：内部网络没有网关；Agent 到虚拟机各地址的连接都被本地拒绝（没有路由）；网卡上没有 IPv6 地址；对照成立。
     - 无法验证：超时、结果缺失、网络设置读不到。
4. **DNS 和 Docker 接口两项不再把子网的 `.1` 当网关**
   - 原来的脚本按“子网的第一个地址就是网关”去探网关上的 53 和 2375/2376。新网络里 `.1` 是 Agent 自己，探到的是自己的端口；Agent 自己在 2375 上起服务时，Docker 接口一项还会误报。
   - 现在由宿主把 Docker 记录的网关传给脚本，没有网关就不探。

本分支从 `feat/isolation-checks`（PR #76，未合并）切出，在它的隔离检查结构上加第 10 项。

## 真机验证（2026-10-31，演示机，Docker 29.5.2）

### 先确认现象和修法

用一次性网络和 Agent 镜像起的容器（只读根、去掉全部权限、Agent 用户）对比两种建法，测完已删除。

| | 原来的建法（`--internal`） | 新建法（加 `inhibit_ipv4`） |
| --- | --- | --- |
| Docker 记录的网关 | 有，子网的 `.1` | 没有 |
| 虚拟机网桥上的地址 | `.1` 和 IPv6 链路本地地址 | 只有 IPv6 链路本地地址 |
| 容器连子网 `.1` 的 22 端口 | 连上，拿到 `SSH-2.0-OpenSSH_9.6p1` | `.1` 是这个容器自己，拒绝连接 |
| 容器连网桥的链路本地地址的 22 端口 | — | 本地拒绝：Docker 关掉了容器网卡的 IPv6（`disable_ipv6=1`） |
| 固定 `.2`、别名 `gatekeeper` 的门卫样容器 | — | 解析和连接都正常 |

虚拟机的 sshd 监听 `0.0.0.0:22` 和 `[::]:22`，所以网桥上只要有地址就能连到。

### 新建沙箱 `uat-vmgw-new`

本分支的 cagectl 创建：Codex 绑定七牛 xapi，启用 DeepWiki（公开远程 MCP）。

- **网络**：内部网络没有网关、带选项，门卫 `192.168.192.2`，Agent `192.168.192.1`，虚拟机网桥上没有 IPv4 地址。出网网络照旧：网关 `192.168.208.1`，门卫 `192.168.208.2`。
- **Agent 连虚拟机**：
  - 子网 `.1` 的 22 端口拒绝连接，那是 Agent 自己；
  - 虚拟机在出网网络（`192.168.208.1`）、虚拟机自己的网卡（`192.168.5.1`）、docker0（`172.17.0.1`）上的 22 端口都本地拒绝（`ENETUNREACH`）；
  - 门卫的 8888、8890 能连上；8899 拒绝连接，管理端口只在出网网络上。
- **经门卫的请求**（`cagectl sandbox exec` 里用 curl）：
  - 模型：`POST https://xapi.qiniu.io/v1/responses` 返回 200，`gpt-6.1-sol` 回复 OK；
  - MCP（`http://gatekeeper:8890/mcp/deepwiki`）：initialize 返回 200（DeepWiki 2.14.3）。授权 `read_wiki_structure` 后，tools/list 只列出这一个工具，调用它查 `elazarl/goproxy` 拿到了文档目录；调用未授权的 `ask_wiki_question` 被门卫拒绝。
- **隔离检查 10 项**：9 项通过；“直连数据库”没启用数据库服务，跳过。
  - “虚拟机网关端口”的证据：内部网络上没有虚拟机的地址；Agent 连 `192.168.208.1` 的 13 个端口都本地拒绝；网卡上没有 IPv6 地址。
  - 对照：出网侧对照容器连上了 `192.168.208.1:22`。
- **能不能报出问题**：`TestIsolationChecksCatchBrokenSandboxes` 加了一种配错方式“Agent 接在虚拟机所在的网络上”（探针容器扮演 Agent，接在出网网络上）。它报“Agent 连上了虚拟机 192.168.208.1 的 22 端口”；原有五种配错方式也都还报问题。

## 顺带发现：虚拟机里的 Docker 网段快用完了

- **现象**：建第三个测试沙箱时，出网网络建不出来，报 `all predefined address pools have been fully subnetted`。
- **原因**：Docker 默认的地址池约 31 个网段：172.17—172.31 共 15 个 /16，192.168.0.0/16 切成 16 个 /20。docker0 占一个，每个沙箱占两个；演示机上已有 12 个沙箱，最多还能再建两三个。
- **和本改动的关系**：迁移先删旧网络再建新的，不多占网段，这次重建拿回的都是原来的网段。网段恰好被别处占完时，迁移会停在“旧网络已删、新网络没建出来”，腾出网段后再启动即可恢复。
- **处理**：测试沙箱验证后已删除，网段数恢复到测试前。给专用实例的 Docker 配更小的 `default-address-pools`，或者建网络时显式指定小网段，可以作为后续改进。

## 范围与限制

- 只覆盖 IPv4 上这 13 个 TCP 端口；UDP 只在 DNS 一项里测 53。
- **IPv6**：Docker 关掉了 IPv4 网络上容器网卡的 IPv6，网桥的链路本地地址到不了。检查只看 Agent 网卡上有没有 IPv6 地址，没有主动探测链路本地地址。
- **不在这项里**：容器逃逸；宿主 Mac 上的服务（“宿主回环”探针仍未做）；门卫本身（Agent 本来就要连门卫的 8888 和 8890）。
- **迁移时机**：迁移在下一次启动时发生。还没重启的旧沙箱仍在旧网络上，“虚拟机网关端口”会对它们报“发现问题”。
- **依赖 Docker 的行为**：Docker 29.5.2 下加了这个选项的网络没有网关。如果别的 Docker 版本仍保留网关，这项检查会报“发现问题”，不会静默通过。
