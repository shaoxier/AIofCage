# 隔离检查补对照验证

[验收记录索引](README.md)

## 改动

对应第二轮会议第 8 条和 [todo 清单](../round2/todo.md)第 8 项（P0-4）的最小版本：补上 DNS、Docker 接口、项目边界三类探针，每类都带正向对照；计数改为按状态分别统计。

1. **对照结构**
   - 每项结果多了“对照”列表。对照是一个必须能看到问题的环境，用来证明探针本身有效。
   - 任何一项对照不成立，“通过”一律改判“无法验证”。这条规则在宿主统一执行，不依赖检查脚本自己判断。“发现问题”不受影响。
2. **DNS 查询外传**（替换原来的“公网 DNS 连通性”，原来那项在 Docker 自定义网络上永远判不了“通过”）
   - **金丝雀**：在沙箱的出网网络上临时起一个 DNS 服务，代表“虚拟机以外”，只记录带本次随机串的查询名。它能看到两类查询：直接发给它的，以及 Docker 内嵌 DNS 转发给它的。
   - **三个对照**：
     - 出网侧对照容器直接发给金丝雀，必须被记到；
     - 经内嵌 DNS 转发给金丝雀，必须被记到；
     - 虚拟机本身能解析公网域名。这一条是 Agent 解析 example.com 失败的前提，否则失败不说明问题。
   - **反例**：内部网络上的探针容器，DNS 指向金丝雀，它的查询不能被记到。它比 Agent 的实际配置更严：即使 DNS 配错了，查询也出不去。
   - **Agent 自己**：
     - Agent 的内嵌 DNS 只转发到它容器里的 127.0.0.1，金丝雀看不到这条路。这条路靠“解析 example.com 必须失败”判断，所以有上面第三个对照。
     - 另外测：直连金丝雀；UDP 53 直连 223.5.5.5 和 8.8.8.8；TCP 53；DoT 853；IPv6 UDP 53；内部网关和门卫上的 UDP/TCP 53（防止虚拟机里有转发 DNS）。
   - **确定性检查**：读 Docker 的设置，Agent 只接内部网络、DNS 上游只有 127.0.0.1。
   - **判定**：
     - 发现问题：金丝雀记到 Agent 或反例的查询；任何一方得到应答或解析到测试域名；连上任何 DNS 服务；解析到公网域名；Docker 设置不符。
     - 通过：公网目标都被本地拒绝（没有路由）、公网域名解析失败、三个对照都成立。
     - 无法验证：公网目标超时之类的不确定结果。
3. **Docker 接口**（从原来的“宿主测试文件与 Docker 接口”拆出）
   - 查看环境变量 `DOCKER_HOST`、`CONTAINER_HOST`，挂载表，根目录下 5 层以内的 socket 文件（不进项目、`/usr`、`node_modules` 等目录）和已知路径。
   - 只对挂进来的、或者名字像容器运行时（docker、containerd、podman、buildkit、Lima）的 socket 发 `GET /_ping`，其他程序的 socket 只计数。
   - 对本机回环、门卫和内部网关的 2375/2376 端口发 `GET /_ping`。门卫和网关上只要有服务在听就算问题；本机回环只看是不是 Docker 接口，因为 Agent 自己可能在那里起服务。
   - 两个阳性样本：
     - Agent 容器里临时放一个假接口，扫描必须找到它，结论里排除它。假接口不用 docker 这类名字，同时进行的其他检查也会排除它。
     - 另起一个对照容器，像常见的误配置那样把假接口挂到 `/var/run/docker.sock`，扫描必须检出。
4. **项目边界**（从原来的“宿主测试文件与 Docker 接口”拆出）
   - 原来的哨兵放在 macOS 临时目录，虚拟机本来就看不到，测不出边界。
   - 现在宿主在 `~/CageWorkspace/.aiofcage-probe-<随机串>/` 放哨兵，与项目并列，检查后删除。对照：虚拟机里的对照容器能读到它。
   - Agent 侧读挂载表，要求共享目录（`~/CageWorkspace` 的 virtiofs）只挂了项目本身，并且挂的正是项目在共享目录里的那个子目录。
   - 用每个共享挂载推算哨兵会出现在哪里，逐个确认看不到。
   - 列出项目各级上级目录里能看到的条目，除了通往项目的那一级，多出任何条目都判“发现问题”。
5. **直连数据库可以判定了**
   - 原来 Agent 里没有 DNS，`host.lima.internal` 解析不了，这一项永远“无法验证”。
   - 现在由出网侧的对照容器解析出地址并试连（同时说明数据库开着），Agent 连同一个 IP。
6. **新增“绕过网关直连远程 MCP”**（todo 第八节 1 的自检项）
   - 不带任何凭据，经代理逐个请求每个远程 MCP 服务的地址。
   - 只有门卫在请求发出前就拒绝（`default_deny`、`rule_denied`、`port_denied`、`plain_http_denied`、`target_mismatch`）才算通过。
   - 请求到过服务，包括服务返回 401、跳转被门卫拦下（`redirect_denied`）、门卫连上游失败，都算发现问题。
7. **计数改对**
   - 运行状态页原来显示“x/y 项通过”，把跳过和无法验证也算进了分母。
   - 现在和检查对话框一样，显示“通过 9 · 发现问题 0 · 无法验证 0 · 跳过 0”。
8. **临时容器**
   - 用 Agent 的同一个镜像：只读根、去掉全部权限、`no-new-privileges`、内存和进程数上限，带沙箱标签。
   - 不挂项目、home 卷或虚拟机的 Docker socket，用完即删。
   - 金丝雀、DNS 对照和数据库对照接在出网网络上，可以直接上网；它们只运行 Python 标准库（`python3 -I -S`），不运行镜像里的智能体。
   - 后台探针两分钟后自己退出，并带 `--rm`，应用中途崩溃也不会一直留着。
   - 运行状态的采样跳过探针容器。
   - 每次检查开始、停止沙箱、删除或重置沙箱时，都会清理遗留的探针和卷；检查项目边界前，清理十分钟前遗留的测试目录。
   - 同一个沙箱同时只能跑一次检查。
9. **检查脚本**
   - 所有在 Agent 容器里跑的检查脚本（包括原有的几项）都改用 `python3 -I -S`。
   - 原因：项目根目录里的 `json.py` 之类的文件会顶替标准库，原来会让所有检查变成“无法验证”。

## 顺带发现：Agent 能连到虚拟机的 SSH 端口

- **现象**：实测 Agent 容器能 TCP 连上内部网关（虚拟机在内部网络上的地址）的 22 端口，也就是虚拟机的 sshd。原因是发往网桥自身地址的流量走虚拟机的 INPUT 链，Docker 的隔离规则只管转发。其他常见端口（53、2375、2376、8888、8899、8890、10250）都是拒绝连接。
- **风险**：
  - colima 的 SSH 私钥在 Mac 上，不在共享目录里，Agent 拿不到，所以现在登录不进去；
  - 但这让 Agent 多了一个可达的系统服务，sshd 一旦出现无需登录的漏洞，就可能从容器进到虚拟机。
- **可选修复**：
  - 实验确认：内部网络用 `com.docker.network.bridge.inhibit_ipv4=true` 创建后，虚拟机在这个网络上没有地址，容器之间照常互通。
  - 改动涉及已有沙箱的网络重建，不在本项范围内，记为后续事项。
  - 后续已修复，见[内部网络去掉虚拟机地址](2026-10-31-vm-gateway.md)。
- **本次没有加这项检查**：管理面和网关端口探针见下文的限制。

## 范围与限制

- **这次没做的探针**：IPv6 正向对照与公网 IPv6、管理面（门卫管理端口、网关上的服务端口）、跨沙箱、宿主回环。
- **DNS**：
  - 金丝雀代表“虚拟机以外”，没有用团队自有域名的权威 DNS 做外部对照；
  - 虚拟机解析不了公网域名时（例如断网），DNS 这一项只能判“无法验证”；
  - DNS 以外的隧道不在这项里，例如经允许的 HTTPS 域名外传。
- **出网侧探针的剩余风险**：出网侧探针用的是 Agent 镜像里的 Python。如果镜像在构建时就被投毒（例如智能体安装脚本改了 Python 本身），这些探针会在检查的几秒里替它上网。这和投毒后的智能体本身是同一类供应链风险，没有单独处理。
- **Agent 能干扰检查**：检查脚本在 Agent 容器里以 Agent 用户运行，已经被控制的 Agent 能干扰结果。检查验证的是配置，不是抵御恶意 Agent。
- **结果不落盘**：结果仍只保存在应用内存里，界面没有导出按钮；验收用的 JSON 由上面的测试命令导出。
- **数据库直连**：只尝试 TCP 连接，不登录。出网侧对照连不上数据库时只写进证据，不影响结论，因为本地拒绝不依赖数据库是否开着。
