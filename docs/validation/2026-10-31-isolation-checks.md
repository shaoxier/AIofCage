## 改动

对应第二轮会议第 8 条和 [todo 清单](../round2/todo.md)第 8 项（P0-4）的最小版本：补上 DNS、Docker 接口、项目边界三类探针，每类都带正向对照；计数改为按状态分别统计。

1. **对照结构**
   - 每项结果多了“对照”列表。对照是一个必须能看到问题的环境，用来证明探针本身有效。
   - 任何一项对照不成立，“通过”一律改判“无法验证”。这条规则在宿主统一执行，不依赖检查脚本自己判断。“发现问题”不受影响。
2. **DNS 查询外传**（替换原来的“公网 DNS 连通性”，原来那项在 Docker 自定义网络上永远判不了“通过”）
   - 在沙箱的出网网络上临时起一个“金丝雀”DNS 服务，代表“虚拟机以外”，只记录带本次随机串的查询名。
   - 两个对照：出网侧的对照容器直接发给金丝雀、经 Docker 内嵌 DNS 转发给金丝雀，都必须被记到。
   - 一个反例：内部网络上的探针容器，DNS 指向金丝雀，查询不能被记到。它比 Agent 的实际配置更严：即使 DNS 配错了，查询也出不去。
   - Agent 自己：直连金丝雀；经内嵌 DNS 解析；UDP 53 直连 223.5.5.5 和 8.8.8.8；TCP 53；DoT 853；IPv6 UDP 53。另外解析一次 example.com，金丝雀容器同时报告虚拟机能不能解析公网域名。
   - 判定：
     - 金丝雀记到 Agent 或反例的查询、Agent 连上任何公网 DNS、或解析到公网域名，判“发现问题”；
     - 直连都被本地拒绝（没有路由）、公网域名解析失败、两个对照都成立，判“通过”；
     - 有超时之类的不确定结果，判“无法验证”。
3. **Docker 接口**（从原来的“宿主测试文件与 Docker 接口”拆出）。检查以下几处，对找到的每个 socket 和端口发 `GET /_ping`：
   - 环境变量 `DOCKER_HOST`、`CONTAINER_HOST`；
   - 挂载表里的 socket；
   - 根目录下 5 层以内的 socket 文件，不进项目、`/usr`、`node_modules` 等目录；
   - 已知路径（docker、containerd、podman、buildkit、Lima）；
   - 本机回环、门卫和内部网关的 2375/2376 端口。

   两个阳性样本：
   - Agent 容器里临时放一个假 Docker 接口，扫描必须找到它，结论里排除它；
   - 另起一个对照容器，像常见的误配置那样把假接口挂到 `/var/run/docker.sock`，扫描必须检出。
4. **项目边界**（从原来的“宿主测试文件与 Docker 接口”拆出）
   - 原来的哨兵放在 macOS 临时目录，虚拟机本来就看不到，测不出边界。
   - 现在宿主在 `~/CageWorkspace/.aiofcage-probe-<随机串>/` 放哨兵，与项目并列，检查后删除。对照：虚拟机里的对照容器能读到它。结论：Agent 看不到它。
   - 同时列出项目各级上级目录里 Agent 能看到的条目，除了通往项目的那一级，多出任何条目都判“发现问题”。
5. **直连数据库可以判定了**
   - 原来 Agent 里没有 DNS，`host.lima.internal` 解析不了，这一项永远“无法验证”。
   - 现在由出网侧的对照容器解析出地址并试连（同时证明数据库开着），Agent 连同一个 IP。
6. **新增“绕过网关直连远程 MCP”**（todo 第八节 1 的自检项）
   - Agent 带测试令牌经代理直接请求远程 MCP 的地址。门卫拒绝才算通过。
   - 门卫放行时，任何上游应答都判“发现问题”，包括上游返回的 401。
7. **计数改对**
   - 运行状态页原来显示“x/y 项通过”，把跳过和无法验证也算进了分母。
   - 现在和检查对话框一样，显示“通过 9 · 发现问题 0 · 无法验证 0 · 跳过 0”。
8. **临时容器**
   - 用 Agent 的同一个镜像，限制与 Agent 相同：只读根、去掉全部权限、`no-new-privileges`、内存和进程数上限。
   - 带沙箱标签，不挂项目、home 卷或虚拟机的 Docker socket，用完即删。
   - 删除或重置沙箱时，先清理检查中途退出留下的探针，再删网络。

## 顺带发现：Agent 能连到虚拟机的 SSH 端口

- **现象**：实测 Agent 容器能 TCP 连上内部网关（虚拟机在内部网络上的地址）的 22 端口，也就是虚拟机的 sshd。原因是发往网桥自身地址的流量走虚拟机的 INPUT 链，Docker 的隔离规则只管转发。其他常见端口（53、2375、2376、8888、8899、8890、10250）都是拒绝连接。
- **风险**：
  - colima 的 SSH 私钥在 Mac 上，不在共享目录里，Agent 拿不到，所以现在登录不进去；
  - 但这让 Agent 多了一个可达的系统服务，sshd 一旦出现无需登录的漏洞，就可能从容器进到虚拟机。
- **可选修复**：
  - 实验确认：内部网络用 `com.docker.network.bridge.inhibit_ipv4=true` 创建后，虚拟机在这个网络上没有地址，容器之间照常互通。
  - 改动涉及已有沙箱的网络重建，不在本项范围内，记为后续事项。
- **本次没有加这项检查**：管理面和网关端口探针见下文的限制。

## 范围与限制

- **这次没做的探针**：IPv6 正向对照与公网 IPv6、管理面（门卫管理端口、网关上的服务端口）、跨沙箱、宿主回环。
- **DNS**：
  - 金丝雀代表“虚拟机以外”，没有用团队自有域名的权威 DNS 做外部对照；
  - DNS 以外的隧道不在这项里，例如经允许的 HTTPS 域名外传。
- **Agent 能干扰检查**：检查脚本在 Agent 容器里以 Agent 用户运行，已经被控制的 Agent 能干扰结果。检查验证的是配置，不是抵御恶意 Agent。
- **结果不落盘**：结果仍只保存在应用内存里，界面没有导出按钮；验收用的 JSON 由上面的测试命令导出。
- **数据库直连**：只尝试 TCP 连接，不登录。出网侧对照连不上数据库时只写进证据，不影响结论，因为本地拒绝不依赖数据库是否开着。
